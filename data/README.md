# `data/` — what every file in here is

Two layers, both committed:

```
remote sources  ->  data/raw/ (cached verbatim)  ->  data/*.csv (tidy)  ->  FINDINGS.md, docs/answers/
```

`data/raw/` is the evidence as published — never edited, never regenerated by
hand. The top-level CSVs are derived and disposable: delete any of them and the
script named below rebuilds it. To force a re-download, delete the specific file
in `data/raw/`; there are no cache-busting flags.

**One exception:** `data/raw/proposed_gtfs/` was supplied by PRT directly and
exists at no URL. It cannot be re-fetched. Deleting it loses it.

For where each source comes from and what it is authoritative for, see
`DATA_SOURCES.md`. This file is the inventory of what is on disk.

### From `ingest_blr.py` (run this first; everything else reads its output)

**`route_crosswalk.csv`** — the Find My Route HTML table. `current_route`,
`draft2_route`, `final_route`, `category` (Modified 73, Discontinued 20, New
14), `related_routes`, and the `route_page` URL for the plain-language bullets.
The join key for almost everything else. A `current_route` cell may name several
routes (`"86, 77"`); the parser splits them, a naive read loses one silently.

**`service_levels.csv`** — the three Frequency & Hours PDFs, one row per route
per day type (weekday / saturday / sunday). `start_time`–`end_time` is the
published span; `early_4_6a` … `owl_11p_4a` are headways in minutes, blank where
the route does not run in that period. `is_new` marks routes with no current
counterpart.

Since PRT's proposed GTFS arrived this is a **published cross-check, not the
primary frequency source**. Two known biases: the published span end is the last
departure from the anchor rather than from the route, running a median 96
minutes early; and span ÷ headway cannot express a midday gap, so peak-only
routes look like they run all day. `verify_proposed_gtfs.py` measures both.

**`proposed_stops.csv`** — 7,036 stops from the Remix map: `stop_uuid`,
`gtfs_stop_id`, name, lat/lon, wheelchair flag. This is an **inventory, not a
service list** — 1,416 of these stops are on no proposed route. Filter through
`proposed_stop_sequences.csv` before mapping anything.

**`proposed_stop_sequences.csv`** — 10,464 stop-visits over 200 route
directions: `route_id`, `pattern`, `direction`, `headsign`, `stop_sequence`,
`stop_uuid`, `meters_from_start`. The sequence half of `stop_times.txt` with no
times attached — Remix publishes no timetables.

**`current_routes.csv`** — `routes.txt` out of the published current GTFS,
unmodified. The before-side route list, including rail and the inclines.

**`exhibit_a.txt`** — `pdftotext -layout` of Exhibit A, the document PRT is
legally required to notice. Quote from here when the question is what PRT
formally proposed rather than what the data shows.

### Analysis outputs

**`stop_service_change.csv`** — one row per currently served stop. `status` is
`kept` (4,568), `kept_nearby` (344 — the stop id vanished but the proposal
serves a stop within 150 m) or `loses_all_service` (870), with
`metres_to_nearest_proposed_stop` showing the work. `confidence` is `confirmed`
(5,766) or `unverifiable` (16 — served today, absent from Remix, possibly added
after Remix's 2023 base feed); the unverifiable tier never enters a headline.
Boardings are carried per day type for weighting.

Proposed side is **Remix**, not the proposed GTFS — this script has not been
moved over yet, so its stop inventory is the 2023-base one.

**`stop_frequency_change.csv`** — how much service each location has, not merely
whether it has any. `current_trips` / `proposed_trips` / `pct_change` are
weekday trips within 400 m; the `_150m` columns are the strict same-corner
sensitivity. `cur_*` / `prop_*` period columns break the day into the seven
published periods. Both sides are counted from real GTFS `stop_times` by the
same code, a trip counted at the stop it calls at and at its departure time
there.

**`coverage_change.csv`** — the widest file here, and the one behind
`COVERAGE-CHANGE` and `STOP-LOST-SERVICE`. Per location it carries weekday /
Saturday / Sunday trips both ways, weekday trips by period, both route lists,
and then the five BASE_CAMP tiers as 0/1 flags for each network:
`{cur,prop}_week_any_minimum`, `_weekdays_any_minimum`, `_weekends_any_minimum`,
`_week_any_hourly`, `_weekend_any_hourly`, each repeated with a `_150m` suffix.
`hourly` means a **maximum** gap of 60 minutes anywhere in 6am–6pm on the better
direction — counting the wait from 6am to the first departure and from the last
to 6pm — not an average, which peak-only service would pass.

**`stop_route_replace.csv`** — the "different bus, same corner" case: locations
keeping comparable weekday trip counts while the routes serving them change.
`routes_lost` / `routes_gained` after translating renumbering away. These are
riders who must relearn the network without losing service.

**`route_service_days.csv`** — one row per modified route.
`current_days` / `proposed_days` are `weekday;saturday;sunday` sets;
`proposed_days_with_variants` folds in the S-variants (29S, 53S, 55S, 69S, 78S,
89S), which is where several corridors' weekend service actually went. Quote
`days_lost_corridor` / `days_gained_corridor` rather than `days_lost` /
`days_gained` — the route-wise columns read a variant as a loss it is not.
`riders_weekday/saturday/sunday` weight the change.

**`oneseat_change.csv`** — one row per place × anchor, 186 for Downtown and 183
for Oakland. `status` is `keeps` (242), `gains` (20), `loses` (27) or
`none either way` (80), with `routes_kept` / `routes_lost` / `routes_gained`
naming the routes responsible. The unit is the place — city neighbourhood, else
municipality — because per-stop the adjacent stop ids on a corridor split the
route set and manufacture losses. PRT's `HOOD`/`MUNI` labels are outlier-filtered
first; they mislabel some stops by up to 40 km.

**`discontinued_route_ridership_202604.csv`** — WPRDC average riders by day type
for each of the 20 discontinued routes, April 2026. Preferred over stop-level
sums for any route total: official, weighted, and eleven months fresher.

### ⚠️ `route_frequency_change.csv` — orphan, stale

**No script in this repo writes this file.** It is a route-to-route trip
comparison from an earlier iteration, and it predates both the 8–11pm headway
column fix (`FINDINGS.md` caveat 9, which had 16 routes' late-evening headway
wrong) and the proposed GTFS. `docs/answers/locations/OUTER-CHARTIERS.md` cites
it with that caveat attached; `LOSE/GAIN-SERVICE-HOURS` is marked blocked in
`docs/answers/README.md` pending a re-added route-level rollup. Do not quote it
without the caveat, and do not use it to compare route N to route N — the plan
re-splits corridors, so that comparison is invalid regardless of vintage.

**`proposed_gtfs/`** is the only source here that cannot be re-downloaded — PRT
emailed it six days before the Proposed Final Network was published, and nothing
on the feed itself proves it is the final plan. `verify_proposed_gtfs.py` earns
that claim against the documents PRT did publish: route set, day types and span
must agree with the Frequency & Hours PDFs (they do), while trip volume is
expected to disagree and the size of the disagreement is why the feed supersedes
the PDF model. Contents: `Future_BLR_Service-Weekday/-Sa/-Su` calendars over
2027, 5,515 stops, 14,488 trips, 698,865 `stop_times` rows.

**`stop_usage_202505.csv`** is 19,854 stop × route rows over 7,076 stops. Two
traps: take boardings from the `All Routes` row (summing the per-route rows
double-counts), and quote PRT's own disclaimer — these are "unadjusted,
unofficial totals" that may understate ridership by as much as 30%. Boardings
only; alightings stopped in September 2023.

## Rebuilding

```bash
python3 ingest_blr.py               # must run first
python3 analyze_service_loss.py
python3 analyze_route_ridership.py
python3 analyze_frequency_change.py
python3 analyze_one_seat.py
python3 analyze_coverage_change.py
python3 verify_proposed_gtfs.py     # checks the supplied feed against the PDFs
```

`analyze_one_seat.py` reads only raw sources and runs independently.
`gtfs.py` is the shared reader both networks are measured through — it is
imported, not run.

## Reading anything in here

Four conventions carry across every file; each was arrived at because the naive
version produced a wrong answer with a confident face on it. `CLAUDE.md` has the
full list.

1. **Never compare route N to route N.** The plan re-splits corridors. The unit
   is a location or a place, with the same walk radius applied to both networks.
2. **Aggregate above the stop id.** Adjacent stop ids split a route set at
   corridor locations. Stop-level rows are an intermediate, not a finding.
3. **Report both radii where they disagree.** 400 m is the headline
   quarter-mile access distance, 150 m the strict same-corner test; where they
   part company, the plan is consolidating stops.
4. **State the vintage.** Stop boardings are May 2025 and boardings-only; route
   ridership is April 2026; the current network is a summer 2026 feed and the
   proposed one is dated 2027.
